# Техническое задание на доработку Resolve Assistant

Дата: 30 октября 2026 года.

Работать с существующей реализацией в `plugin/` и `lib/`, сохраняя результаты пользователя.

## 2. Подтверждённые требования пользователя

1. Текст речи получать из DaVinci. Не добавлять отдельный платный сервис распознавания или API-ключ для STT.
2. Если видеоконтекст существует и включён для отправки сообщения, длительность моушен-графики определяется этим диапазоном.
3. В параметрах клипа показывать эту длительность с округлением до десятых и блокировать ручное изменение.
4. При наведении показывать объяснение блокировки и способ изменить длительность через In/Out.
5. При отключении видеоконтекста поле длительности разблокируется. Это последствие должно быть явно объяснено пользователю.
6. Новая видимая версия создаётся только кнопкой «+» у списка версий.
7. После «+» открывается собственный чат новой версии, например V2. В нём пользователь пишет запрос на изменение.
8. Новая версия знает, что было сделано в родительской версии, и сохраняет доступ к её исходникам, ассетам и существенному контексту.

Далее технические решения, не оговорённые пользователем дословно, сформулированы как рекомендуемый способ выполнить эти требования без потери данных.

## 3. Получение речи из DaVinci

### 3.1. Что сейчас ограничено

`plugin/bridge.cjs`, функция `readTimelineTranscript()`, получает только `timeline.GetMediaPoolItem().GetTranscription()` и отбирает слова по In/Out. Само распознавание не запускается. Расшифровки исходных клипов отдельно не собираются, вложенный вариант получения не проверяется.

В одном из ранее сохранённых реальных запросов было `speechIncluded: false`, 0 фрагментов текста и 2 кадра. Это подтверждает отсутствие речи в том конкретном запросе, но не доказывает недоступность расшифровки во всём Resolve.

Документация установленного SDK:

```text
C:\ProgramData\Blackmagic Design\DaVinci Resolve\Support\Developer\Scripting\DaVinciResolveScript.pyi
C:\ProgramData\Blackmagic Design\DaVinci Resolve\Support\Developer\Scripting\CHANGELOG.md
```

В установленной версии описаны:

```text
MediaPoolItem.GetTranscription(useNestedClipTranscription=False)
MediaPoolItem.TranscribeAudio(useSpeakerDetection=None, transcribeAsNestedClip=False)
Timeline.GetMediaPoolItem()
Timeline.GetItemListInTrack(trackType, index)
TimelineItem.GetMediaPoolItem()
TimelineItem.GetSourceStartFrame() / GetSourceEndFrame()
TimelineItem.GetSourceStartTime() / GetSourceEndTime()
```

`GetTranscription` добавлен в scripting API 21.1. Формат расшифровки содержит `segments`, а сегменты — `start`, `end`, `text`, `speaker`, `words`. Времена слов и сегментов представлены строковыми таймкодами. Совместимость конкретных вызовов с установленным JavaScript Workflow Integration проверять на живом SDK: наличие метода в Python-описании само по себе не является проверкой выполнения через JS.

### 3.2. Требуемый поток

- При включённом контексте сначала попытаться получить существующую расшифровку подходящего MediaPoolItem, включая поддерживаемый вложенный вариант.
- Если готового текста нет, использовать распознавание самого DaVinci. Запускать его при подготовке явно отправленного сообщения, а не в фоновом опросе интерфейса каждые несколько секунд.
- Проверить возможность расшифровать таймлайн как вложенный клип. Если это корректно работает, такой путь предпочтителен для получения текста в координатах итогового таймлайна.
- При необходимости собирать существующие расшифровки исходных клипов, пересекающих In/Out, с пересчётом их времени в координаты таймлайна.
- Отправлять модели только текст, относящийся к выбранному диапазону. Не отправлять всю расшифровку длинного исходника из-за короткого выделения.
- Не запускать транскрибацию всего Media Pool или всех папок проекта.

Особенности реализации:

- SDK может распознавать MediaPoolItem целиком, а не только In/Out. Не выдавать это за распознавание исключительно выделенного фрагмента. После обработки всё равно отбирать только нужный текст.
- Не очищать и не заменять существующую расшифровку пользователя.
- Учитывать начало таймлайна, исходный таймкод, подрезку клипа, FPS источника и таймлайна, drop-frame и границу конца диапазона.
- При работе с исходными клипами учитывать отключённые клипы и аудиодорожки; не включать явно выключенный звук как услышанную речь.
- Для ретайминга, reverse, compound/multicam и других сложных случаев использовать корректное отображение времени либо явно сообщать о неподдержанном случае. Не привязывать слова к случайным временам.
- Слова, пересекающие границу выделения, обрабатывать согласованно; не терять целые предложения только потому, что один сегмент шире In/Out. Сначала использовать пометки отдельных слов, если они доступны.
- Молчание `(...)` не считать речью. Удалять дубли при пересечении источников или повторном чтении.
- Показать прогресс ожидания Resolve; добавить ограничение времени и обработку ошибки.
- Отмена должна остановить дальнейшую подготовку/отправку модели. Если SDK не умеет прерывать уже запущенное распознавание, не обещать его фактическую остановку: игнорировать поздний результат и не отправлять отменённое сообщение в AI.
- После ожидания повторно проверить проект, таймлайн и ключ диапазона. Не подменять контекст на изменившийся.

Не утверждать без отдельной проверки, что подписка ChatGPT вообще не поддерживает распознавание речи. Для этой задачи достаточно существующую подписку оставить для диалога/генерации, а речь получать средствами DaVinci.

### 3.3. Понятные состояния интерфейса

Не смешивать отсутствие речи, отсутствие расшифровки и ошибку SDK. Нужны различимые состояния:

| Состояние | Пример подписи |
|---|---|
| Ещё не подготовлено | «Речь будет получена из DaVinci при отправке» |
| Обрабатывается | «DaVinci распознаёт речь…» |
| Текст получен | «Речь из DaVinci · 8 фрагментов» |
| Успешно обработано, речь отсутствует | «В выбранном диапазоне речь не найдена» |
| Метод недоступен или обработка не удалась | «Речь недоступна: … Отправляются только кадры» |

Для полученного текста добавить действие «Показать текст речи» с читаемым просмотром фрагментов и времени. Пользователь должен понимать, какой текст реально попадёт в запрос.

При отсутствии текста кадры могут использоваться дальше, но интерфейс и запрос модели обязаны явно говорить, что речи нет. `speechIncluded` становится `true` только при реально непустом и подходящем диапазону тексте.

## 4. Длительность по видеоконтексту

### 4.1. Условие блокировки

Блокировка действует только при одновременном выполнении двух условий: есть валидный текущий диапазон In/Out и пользователь включил его передачу. При снятой галочке или отсутствии валидного диапазона длительность доступна вручную, если поле не заблокировано текущей операцией.

Длительность диапазона рассчитывать по действующей семантике включённого Out:

```text
rangeDuration = (endFrame - startFrame + 1) / timelineFps
```

В интерфейсе показывать одно десятичное место: например, `1.5`, `8.0`, `23.7`. Не округлять значение в данных до вычисления результата рендера. Рекомендуемое техническое правило: показывать десятые, а экспорт согласовывать с ближайшим целым числом кадров выходного FPS:

```text
outputFrameCount = max(1, round(rangeDuration * outputFps))
outputDuration = outputFrameCount / outputFps
```

Такое разделение округления интерфейса и покадровой длительности — техническая рекомендация для совпадения с монтажом. Разница от диапазона не должна превышать половины кадра выходного FPS.

### 4.2. Поведение поля

- Подставлять длительность диапазона в существующее поле «Длительность, с» и блокировать изменение клавиатурой, стрелками и колёсиком.
- При изменении In/Out обновлять показанное значение, пока контекст включён.
- Запомнить последнее ручное значение отдельно. При отключении контекста вернуть его и разрешить редактирование.
- Хранить ручное значение и режим привязки отдельно от вычисленной длительности. Это должно переживать переключение версий, композиций и перезапуск.
- При повторном включении снова брать актуальную длительность диапазона, а не прежнее значение поля.
- Изменение диапазона/параметров не должно незаметно переделывать уже готовый файл. Сохранённый результат и подпись его предпросмотра описывают фактическую длительность этого результата; панель параметров может описывать следующее изменение текущей версии.
- Сохранённый видеоконтекст старого результата не считать автоматически текущим активным выделением Resolve.

Текст пояснения у заблокированного поля:

> Длительность определяется видеоконтекстом: 8,0 с. Чтобы изменить её, измените In/Out в DaVinci. Отключите видеоконтекст — поле длительности станет доступно.

Текст у действия отключения контекста:

> Убрать видеоконтекст. Длительность снова можно будет изменить вручную.

У выключенного контекста:

> Включить видеоконтекст. Длительность будет взята из In/Out и заблокирована.

Объяснение должно работать при наведении на обёртку поля или значок помощи и быть доступным с клавиатуры. Нативный disabled-input сам по себе может не получать hover/focus: не привязывать всю подсказку только к нему.

### 4.3. Изменения в проверке параметров

Сейчас `lib/motion.cjs:normalizeVideoSettings()` ограничивает длительность 2–15 секундами. В `renderer.js` и HTML тоже есть ограничения и приведение к этому диапазону.

Простая блокировка поля без изменения этих мест недостаточна: реальный контекст уже встречался короче 2 секунд, а другой может быть длиннее 15 секунд.

- Для длительности от видеоконтекста поддержать короткие и длинные диапазоны, не обрезая их молча до 2 или 15 секунд.
- Проверить весь путь: отображение → отправка → controller → нормализация сцены → подготовка движка → сохранение → повторное открытие → рендер.
- Учитывать изменение размеров/частоты вручную: длительность в секундах берётся из контекста, число кадров — из выходного FPS.
- Старые ручные ограничения можно сохранить для обычного ручного режима. Контекстный режим должен обрабатываться явно.
- Источник длительности должен подтверждаться host/controller по актуальному диапазону, а не произвольным флагом или числом от renderer/модели.
- Если существует технический предел рендера, показывать понятную ошибку до генерации, а не подменять длительность. Не придумывать новый лимит без оценки реальных ограничений.

## 5. Версии через плюс и отдельные чаты

### 5.1. Пользовательский сценарий

1. Новая композиция получает начальную логическую версию V1 и её чат.
2. Пользователь обсуждает и создаёт сцену в чате V1.
3. Под предпросмотром рядом с версиями расположена кнопка «+» с подписью/подсказкой «Новая версия».
4. Нажатие «+» создаёт V2 на основе выбранной версии и открывает её отдельный чат.
5. V2 получает основу: сцену, параметры, ассеты и зафиксированный контекст V1. Пользователь пишет, что изменить.
6. Вопрос в чате V2 даёт текстовый ответ. Просьба о правке изменяет результат внутри V2.
7. V3 появляется только после следующего нажатия «+».

Отправка сообщения и `action="revise"` больше не увеличивают номер видимой версии. Не заменять требование другим действием вроде «создать версию» в выпадающем меню самого сообщения.

При переключении V1 ↔ V2 должны переключаться собственная переписка, черновик, параметры, состояние видеоконтекста и соответствующий предпросмотр. Одного общего чата с фильтром по номеру результата недостаточно.

В шапке чата показывать выбранную версию, например «Чат V2». Для дочерней версии показать «Основа: V1». При создании от старой версии основой является именно выбранная версия, а не последняя в списке.

### 5.2. Логическая версия и сохранённый результат

Рекомендуется разделить две сущности:

- **Логическая версия**: V1/V2/V3, отдельный чат, родитель, черновики, настройки, текущий результат.
- **Ревизия результата**: конкретный неизменяемый job с TSX/описанием сцены, assets, MOV и импортами.

Внутри V2 можно несколько раз менять сцену. Для безопасности файлов каждый такой результат может сохраняться как новая внутренняя ревизия/job, но в полосе версий остаётся одна V2. Это рекомендуемый способ не перезаписывать MOV, уже используемый в Resolve.

Не менять существующий `motion.mov` под другим содержимым, если на него уже ссылается Media Pool/таймлайн. Рендер и импорт должны действовать на текущую ревизию выбранной логической версии. Переименование версии/композиции не должно перемещать файлы.

### 5.3. Черновая новая версия

Рекомендуемый сценарий: «+» сразу сохраняет черновую V2 без обращения к модели и без нового MOV. До первой генерации можно показать предпросмотр основы с явной подписью «Основа V1 — V2 ещё не изменена».

Черновая версия не должна выдавать исходный MOV родителя за собственный новый результат. При отсутствии основы с готовой сценой сохраняется пустой предпросмотр и наследуется доступная история обсуждения.

Защитить кнопку от двойного создания при повторном клике/повторе IPC. Номер следующей версии определяется хранилищем, а не только длиной массива на клиенте.

### 5.4. Наследование истории и ассетов

При создании V2 зафиксировать основу на момент нажатия «+»:

- ID родительской версии и конкретной ревизии/job.
- Полный исходник текущей сцены или декларативный план HyperFrames.
- Параметры сцены и необходимые сведения об используемом движке.
- Историю разговора/решений до точки ветвления либо ссылки на неизменяемый снимок этой истории.
- Манифест ассетов и ссылки на существующие проектные файлы, необходимые для продолжения.
- Использованный контекст кадров и речи с явной привязкой к сообщениям/снимкам контекста.

Последующие изменения V1 не должны незаметно менять основу уже созданной V2. Новые сообщения V2 не должны появляться в собственной переписке V1.

Модель должна получать содержимое, нужное для правки: полный актуальный исходник, объяснение основы, существенную историю и поддерживаемые вложения. Одно имя файла, ID или путь не даёт модели знания о содержимом файла, поскольку исполнительные инструменты для неё отключены.

Сохранять ассеты допустимо через ссылки на неизменяемые файлы: не обязательно физически копировать всё дерево в каждую версию. Нельзя удалять файлы, пока от них зависит дочерняя версия.

Служебные бандлы Remotion/GSAP не нужно целиком отправлять в текст модели. Отличать ресурсы исполнения от пользовательских ассетов сцены.

Наследование исходников и ассетов сцены не означает автоматическую отправку выключенного текущего видеоконтекста. Сохранённая история остаётся доступна, но новые кадры/речь прикладываются в соответствии с включением контекста и явно выбранной основой.

### 5.5. Отдельная проблема сохранения контекста

Сейчас материалы `videoContext` сохраняются в `jobs/<id>/context/` внутри `Controller.create()`. Если модель отвечает только текстом и job не создаётся, временный capture удаляется, а независимого постоянного снимка входного контекста сообщения нет.

Для новой схемы этого недостаточно: V2 может наследовать важное обсуждение после вопроса, к которому были приложены кадры и речь.

Вынести сохранение входного контекста в самостоятельную сущность сообщения/версии. После успешного получения и валидации контекст должен быть доступен независимо от того, вернула модель текст или изменённую сцену. Ссылки должны переживать закрытие приложения и создание дочерней версии.

Не переносить временные или произвольные пути от renderer в постоянный манифест без проверки. Файлы авторизации, `.data/auth` и настройки других приложений не являются ассетами.

## 6. Рекомендуемые изменения модели данных и API

Точные имена ниже являются предложением. Важны разделение сущностей и проверяемые связи.

```text
Composition
  id, projectId, name
  versionIds[], selectedVersionId
  schemaVersion

Version
  id, compositionId, number
  parentVersionId, baseRevisionId
  inheritedContextSnapshotId
  ownMessages[]
  selectedRevisionId, revisionIds[]
  draft, settings, manualDurationSeconds
  videoContextEnabled, durationMode
  status: draft | ready

Revision / Job
  id, compositionId, versionId, parentJobId
  plan/source, assetManifestId, contextSnapshotIds[]
  output, imports, createdAt

ContextSnapshot
  id, projectId, versionId, messageId
  rangeKey, timelineId, in/out, duration, sourceFps
  frameFiles[], transcriptSegments[]
  speechStatus, speechSource
```

Предлагаемые операции:

- `version.create({compositionId, baseVersionId, baseRevisionId, requestId})` — только создание новой видимой версии.
- `version.get(...)` / `version.update(...)` — получение и сохранение состояния конкретного чата версии.
- `chat.send({compositionId, versionId, prompt, ...})` — текстовый ответ либо обновление результата внутри указанной версии.

Проверять принадлежность version/job/context/asset текущему проекту и композиции на стороне controller. Поздний результат запроса не должен прикрепляться к версии, открытой пользователем уже после отправки.

Сохранить структурированный ответ модели `reply/revise`, но поменять его смысл в приложении: `revise` обновляет текущую логическую версию через новую безопасную ревизию; новую V2 создаёт только явный `version.create`.

Для истории по-прежнему нужен ограниченный размер запроса. Полная история хранится локально; при сокращении контекста сохранять актуальный исходник, сведения об основе и существенные решения. Указывать модели, если старая часть истории не вошла в запрос. Не обещать бесконечный контекст.

## 7. Миграция и сохранность данных

- Добавить версию схемы хранилища и идемпотентную миграцию.
- Существующие `jobs/<id>/` не перемещать. Пути MOV и записи импорта сохранять.
- Существующие видимые версии преобразовать в логические версии с привязанными результатами. Не сводить их незаметно к одной версии.
- Старую общую переписку сохранить целиком. Где принадлежность сообщения версии однозначна, разнести её по версиям. Не придумывать отсутствовавшие сообщения и связи.
- Если точное разделение старой истории невозможно, сохранить её как явно обозначенную историю до миграции/унаследованный контекст. Не удалять её ради новой структуры.
- Пустой сохранённый чат преобразовать в композицию с черновой V1.
- Исторические unscoped jobs без projectId не назначать случайному проекту при фоновом чтении. Сохранить совместимость и явно определить их безопасную привязку.
- Проверить повторную загрузку: существующий `ConversationStore.load()` автоматически регистрирует jobs как версии. После новой схемы эта логика не должна снова превращать внутренние ревизии в отдельные V3/V4.
- Запись результата и обновление индексов должны быть согласованы. При сбое между операциями восстановление не должно терять результат, дублировать версию или считать частичный job готовым.
- Сохранять обработку повреждённых файлов: один повреждённый чат не отключает весь проект и выбор папки.
- Перед миграцией создать отдельную резервную копию меняемых метаданных, не перезаписывая предыдущую резервную копию другой задачи.

## 9. Ограничения, которые нужно сохранить

- Не менять расположение чата на нижнее и не возвращать переключатель раскладки.
- Не добавлять отдельный API-биллинг или STT-сервис.
- Не выдавать модели доступ к shell, файлам пользователя, credentials или произвольной сети.
- Не выполнять сгенерированный код в Node/Electron host. Действующие проверки TSX, разрешённых импортов и изолированный preview сохранить.
- Не разрешать previewUrl или пути вложений, присланные renderer, без авторитетной проверки controller.
- Не создавать новую видимую версию при вопросе, ответе модели, ошибке, повторе сообщения, рендере или импорте.
- Не терять черновики, ручную длительность и выбранную версию при фоновом обновлении контекста.
- Не закрывать главное окно Resolve и не вносить тестовые изменения в важный монтаж пользователя.

## 10. Критерии приёмки

### Длительность

| Проверка | Ожидаемый результат |
|---|---|
| Контекста нет | Ручное поле доступно |
| Контекст есть, галочка снята | Поле доступно, используется ручная длительность |
| Диапазон 8 секунд включён | Поле заблокировано, показано 8.0, экспорт соответствует диапазону по кадрам |
| Диапазон 1.542 секунды включён | Показано 1.5, генерация не отклоняется из-за старого минимума 2 секунды |
| Диапазон длиннее 15 секунд | Длительность не урезается молча до 15 секунд |
| In/Out изменены до отправки | Значение обновлено; устаревший rangeKey не принимается |
| Контекст выключен после ручных 5 секунд | Возвращается редактируемое ручное значение 5 секунд |
| Контекст включён снова | Взята актуальная длительность диапазона |
| Перезапуск / переключение версий | Режим, ручное значение и сохранённые параметры восстанавливаются |
| Изменён FPS результата | Время сохраняется с погрешностью до половины выходного кадра |
| Hover и клавиатура у поля | Понятно, почему поле заблокировано и как его разблокировать |

### Речь

- Существующая готовая расшифровка попадает в запрос и доступна для просмотра.
- При отсутствии готовой расшифровки проверен запуск поддерживаемого пути средствами DaVinci.
- Проверка выполнена на реальном материале с речью, а не только на mock-объектах SDK.
- Если в тестовом диапазоне нет речи или нужный API не работает, это явно указано в результате проверки; не писать «распознавание работает» по одному тесту со stub-данными.
- В запросе нет текста вне In/Out; проверены подрезка, начало таймлайна, разные FPS и границы слов.
- Нет повторных запусков распознавания при фоновом обновлении интерфейса.
- Ошибка SDK, отмена и изменение проекта не приводят к отправке неверного/чужого текста.

### Версии и чаты

- «+» создаёт одну V2, сразу открывает её чат и не обращается к AI до сообщения пользователя.
- V2 наследует выбранную основу V1 с исходником, ассетами и контекстом.
- Уточняющие вопросы и правки внутри V2 не создают V3.
- Повторный запрос внутри V2 сохраняет доступ к её предыдущему результату, не перезаписывая импортированный MOV.
- Следующее «+» создаёт V3; при выборе V1 перед «+» основой служит V1.
- Переключение версий восстанавливает их собственные сообщения и черновики.
- V2 сохраняет основу после последующего изменения V1.
- После перезапуска дочерняя версия помнит историю и ассеты; временные capture-папки не являются единственным их местом хранения.
- Контекст сообщения с текстовым ответом тоже доступен дочерней версии, даже если при ответе job не создавался.
- Отмена, ошибка записи, повреждённый чат и смена проекта не создают фиктивные версии и не смешивают данные.
- Миграция сохраняет прежние результаты, переписку, пути MOV и импорты. Повторная миграция ничего не дублирует.

## 11. Порядок реализации и проверок

1. Проверить фактические данные и вызовы транскрибации на установленном SDK. Отделить отсутствие текста от ошибки получения.
2. Зафиксировать новую схему «композиция → версии → ревизии» и миграцию. Учесть постоянные снимки входного контекста.
3. Добавить тесты, воспроизводящие требуемое новое поведение и ошибки миграции/восстановления.
4. Реализовать хранилище и server-side операции версий, затем подключить «+» и отдельные чаты.
5. Реализовать доверенное вычисление длительности, поле, восстановление ручного значения и подсказки.
6. Подключить подготовку речи, видимые статусы и просмотр полученного текста.
7. Проверить прежние ограничения безопасности, оба движка, рендер и выбор корректной ревизии для импорта.

Основные команды:

```powershell
npm.cmd test
npm.cmd run check
npm.cmd run smoke
```

Дополнительно проверить рендер контекстного клипа короче 2 секунд и длиннее 15 секунд, восстановление после перезапуска и новый цикл «V1 → + → V2 → вопрос → правка». Браузерные тесты в этой среде могут требовать запуска вне sandbox; не запускать сам Resolve администратором ради тестов.

Обновить README.md, DESIGN.md и краткий отчёт о проверках. После успешных проверок переоткрыть только окно плагина, убедиться в новом интерфейсе на реальном Resolve и сделать скриншот. В отчёте разделить проверенное на живом SDK/модели и проверенное только автоматическими тестами.

Не считать работу завершённой после смены подписей или одного UI-макета: критерии должны выполняться в рабочем плагине, сохраняться на диске и проходить через реальный контроллер.
