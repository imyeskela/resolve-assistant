# Resolve Assistant: установка и обновления на Windows

Дата: 31 октября 2026. Статус: проект решения и этапы работ для ревью; установщик ещё не реализован.

## Что согласовано

- Первый выпуск: Windows x64, DaVinci Resolve Studio.
- Полный EXE с необходимой средой выполнения. Пользователь не устанавливает Git, Node.js или npm.
- Обновление: скачать следующий EXE из GitHub Releases и запустить поверх предыдущей установки.
- Публичный репозиторий: https://github.com/imyeskela/resolve-assistant.
- `master` содержит исходную базу. Планирование и реализация установщика идут в `release/windows-installer`; интеграция через проверенный pull request, без прямых рабочих коммитов в `master`.

Выбор Inno Setup, раскладка каталогов и детали миграции ниже — инженерные предложения, а не уже проверенная реализация. Пользователь выбрал полный EXE и платформу; весь документ ещё подлежит ревью перед реализацией.

## Результат для пользователя

1. Установить DaVinci Resolve Studio отдельно, если его ещё нет. Наш EXE устанавливает Resolve Assistant, не сам DaVinci.
2. Скачать `ResolveAssistant-<version>-windows-x64-setup.exe` из Releases.
3. Сохранить монтаж, закрыть Resolve, запустить EXE и разрешить установку Windows.
4. Открыть Resolve Studio → Workspace → Workflow Integrations → Resolve Assistant.
5. Выбрать папку результатов и подключить свою подписку ChatGPT. Локальный пример/рендер работает без входа; генерация требует интернет и доступ аккаунта.
6. Для обновления повторить шаги 2–4 с новым EXE. Авторизация, настройки, чаты и ссылки на видео сохраняются, кроме случаев истёкшей или недоступной сессии, когда потребуется повторный вход. При самом первом переходе с прототипа может потребоваться заново выбрать UI-предпочтения, если экспорт прежнего localStorage недоступен; установщик/миграция должны объяснить это до подтверждения переноса.

Автоматическое скачивание/установка обновлений, отдельный launcher, фоновые службы, macOS/Linux и установка самого Resolve не входят в первый выпуск. Ссылка на официальный Releases достаточна; проверка новых версий внутри плагина — отдельное последующее улучшение.

## Рассмотренные подходы

| Подход | Плюсы | Ограничения | Решение |
|---|---|---|---|
| Полный Inno Setup EXE | Обычная установка/удаление Windows, зависимости уже в комплекте | Большой файл; для общего каталога плагинов нужен UAC | Рекомендуемая реализация выбранного пользователем полного EXE |
| Небольшой установщик со скачиванием | Меньше первоначальная загрузка | Установка зависит от сети и нескольких источников, сложнее воспроизводимость | Пользователь выбрал полный комплект |
| ZIP / отдельный Electron launcher / MSIX | ZIP удобен разработчикам; отдельное приложение может иметь свой updater | ZIP требует ручной установки; launcher добавляет продукт; MSIX требует доказать интеграцию с внешним Resolve | Не использовать в первом выпуске |

Стандартный Electron autoUpdater не является готовым решением для этого плагина: Electron-процесс принадлежит Resolve, а не нашему отдельно установленному Electron-приложению. Это вывод из архитектуры и [документации Electron](https://www.electronjs.org/docs/latest/api/auto-updater).

## Архитектура поставки

```text
Program Files/Resolve Assistant/
  versions/<version>/
    lib/ plugin/ node_modules/
    runtime/node.exe
    browser/<pinned-build>/
    licenses/ release.json
  current.json

ProgramData/Blackmagic Design/DaVinci Resolve/Support/
  Workflow Integration Plugins/com.local.resolveassistant/
    main.js manifest.xml package.json WorkflowIntegration.node runtime.json

LocalAppData/ResolveAssistant/
  auth/ settings/ codex-profile/ cache/ logs/
  migration-state.json

<выбранные пользователем папки проектов>/jobs/
  <существующие jobs, MOV, .conversations и .contexts>
```

Сохранить ID `com.local.resolveassistant` для совместимости с мостом и существующей установкой. Постоянный Inno `AppId` задать один раз и больше не менять. Program Files и каталог загрузчика должны быть доступны обычному пользователю только для чтения/исполнения; привилегированный установщик не исполняет пользовательские сценарии из старого checkout.

Ввести явные `appRoot`, `dataRoot`, `cacheRoot`, `browserRoot` и `nodePath`. В release-режиме любые записи идут в профиль пользователя или выбранную папку проекта. Режим разработки сохраняет возможность запуска из checkout. Не расширять политику preview и разрешённые возможности генерируемого кода при переносе путей.

Поставлять закреплённый portable Node, production-зависимости с Windows x64 optional/native компонентами, Chrome Headless Shell для закреплённого Puppeteer и согласованный комплект FFmpeg/FFprobe. Не переупаковывать всё в single executable: динамическая компиляция TSX, native binaries и browser assets уже требуют файлов на диске. Никакого `npm install` на компьютере пользователя.

SDK `WorkflowIntegration.node` брать из установленного Resolve пользователя; не включать бинарник разработчика или SDK-документацию в Git/release. Проверять наличие и совместимость, затем копировать локально. Если поддерживаемая версия Resolve меняет SDK, повторный запуск installer в режиме Repair обновляет привязку. Минимальный диапазон поддержки определяется испытаниями; стартовая целевая конфигурация — Studio 21.1.0.14. За её пределами первый installer должен сообщать о неподтверждённой конфигурации и прекращать установку/Repair, пока диапазон не расширен по результатам тестов. Для неподдержанной новой версии Resolve требуется совместимый выпуск Resolve Assistant; обещать Repair старым EXE нельзя.

## Установка, обновление, восстановление

- Проверить ОС/архитектуру, Resolve/SDK, свободное место и целостность payload до изменения рабочей установки. Windows 11 x64 — первоначальная целевая чистая тестовая машина; поддержку Windows 10 не заявлять без проверки и соответствия требованиям Resolve.
- Проверить работающий Resolve и процессы плагина; предложить пользователю сохранить работу и закрыть их. Не завершать их автоматически. Повторить проверку перед переключением версии; при блокировках файлов прекратить обновление.
- UAC нужен только для записи программы и регистрации плагина. Не запускать Resolve, генератор или миграцию с правами администратора. При входе другой учёткой через UAC не трогать её LocalAppData.
- Распаковать новую версию в отдельную папку, проверить файлы/хеши, затем переключить `current.json` и связанные файлы загрузчика. Сохранить прежний указатель, manifest и SDK. Переключение нескольких файлов не считать одной атомарной операцией: нужен журнал установки и восстановление после прерывания.
- При обычной отмене или обрабатываемой ошибке автоматически восстановить предыдущий согласованный набор программы и загрузчика. При аварийном завершении процесса/отключении питания допускается ручной Repair повторным запуском того же installer: файлы прежней версии и журнал сохраняются. Если загрузчик остаётся работоспособным, он выбирает последний согласованный набор; при повреждении самого загрузчика восстановление делает Repair. Никогда не запускать заведомо смешанный набор версий.
- Сохранить предыдущую версию для восстановления. Откат кода не означает откат данных: проверять `dataSchemaVersion` и диапазон чтения схем. До первого изменения формата создавать backup; неподдерживаемый downgrade отклонять.
- Повторная установка той же версии — Repair. Установка более старой версии обычным запуском запрещена; восстановление предыдущей возможно только при совместимости схем и SDK.
- Uninstall удаляет собственные программные файлы и собственный plugin stub. Пользовательские данные, выбранные папки проектов и исходный checkout сохраняются. Очистку данных не включать в обычное удаление.

Стабильный AppId позволяет последующим установкам использовать ту же запись удаления: [Inno Setup AppId](https://jrsoftware.org/ishelp/topic_setup_appid.htm). Настройки пользователя следует создавать из обычного приложения: [administrative install mode](https://jrsoftware.org/ishelp/topic_admininstallmode.htm). Автозакрытие программ необходимо отключить: [CloseApplications](https://jrsoftware.org/ishelp/topic_setup_closeapplications.htm).

## Миграция существующего прототипа

1. Installer сохраняет путь прежнего checkout из старого runtime как справочную метаинформацию, не удаляет checkout и не исполняет его код.
2. Первый обычный запуск предлагает перенести данные из обнаруженного прототипа. Проверить канонические пути; не следовать произвольным junction/symlink и не доверять полям runtime для повышенных операций.
3. В контексте текущего пользователя скопировать необходимые настройки, реестр папок и собственную авторизацию приложения в LocalAppData. Не читать профили других Codex-приложений. Не затирать уже существующие данные новой установки: конфликт требует выбора, по умолчанию сохраняется новая установка.
4. Для DPAPI-сессии проверить расшифровку текущим пользователем; при неудаче сохранить исходник и предложить вход заново.
5. Старый `workspace/jobs` добавить как дополнительный корень; внешние jobs и MOV оставить на прежних абсолютных путях. Предупредить, что checkout нельзя удалять, пока в нём остаются используемые видео.
6. Перенос копированием, уникальные backup и журнал; маркер завершения только после валидации. Повторный запуск не дублирует чаты/корни. Отказ от переноса сохраняет старый checkout и данные, но новый installer уже заменил загрузчик интеграции: старый прототип больше не выбирается автоматически. Объяснить это до установки; для возврата предусмотреть восстановление сохранённого прежнего загрузчика с проверкой доступности checkout.

Отдельно проверить настройки UI в localStorage Electron: текущий host не задаёт собственный userData-путь, а origin file:// изменится. До переноса определить фактическое расположение, сохранить только собственные ключи Resolve Assistant из старого origin и перенести через явную схему настроек; не копировать весь профиль Electron. Если экспорт недоступен, предложить сброс только UI-предпочтений с явным объяснением; чаты/видео не затрагиваются. Начиная с первого EXE, собственные UI-предпочтения хранить через контроллер в `LocalAppData/ResolveAssistant/settings/preferences.json`, чтобы последующие versioned file:// origins не сбрасывали настройки.

## Лицензии, происхождение компонентов и подпись

Публичный репозиторий не означает, что лицензия собственного кода уже выбрана. Выбор лицензии — решение владельца; до него не добавлять MIT/Apache автоматически. Для EXE подготовить инвентарь всех распространяемых компонентов: версия, URL происхождения, хеш, лицензия, notices и требуемые сопутствующие материалы. Нижеследующее — выявленные вопросы, не юридическое заключение.

- Реальные FFmpeg 6.1.1 и FFprobe 4.0.2 текущего прототипа собраны с `--enable-gpl --enable-version3`. MIT у npm-обёртки FFprobe не описывает лицензию EXE. Выбрать согласованный комплект, проверить условия конкретной сборки и предоставить соответствующие исходники/материалы. [FFmpeg legal](https://www.ffmpeg.org/legal.html).
- У Remotion есть собственные условия использования и лицензирования; нельзя обещать всем пользователям безусловно бесплатное использование bundled renderer. Проверить условия распространения именно этого продукта. [Remotion license FAQ](https://www.remotion.dev/docs/license/faq).
- Проверить применимость условий GSAP к распространяемому генератору и HyperFrames, а также notices Node, Chromium, Codex и транзитивных зависимостей. [GSAP Standard License](https://gsap.com/community/standard-license/).
- Разрешение публично перераспространять SDK Resolve пока не установлено; поэтому SDK не является release asset.
- Проверить актуальные условия Inno Setup. [Лицензия](https://jrsoftware.org/files/is/license.txt).
- Предложение для первого технического preview: неподписанный EXE с явным указанием этого в release notes; отсутствие подписи не скрывать. Для стабильного публичного релиза запланировать Authenticode-подпись EXE и uninstaller с timestamp. Сертификата/сервиса подписи пока нет в проекте. Не покупать его автоматически; выбор и расходы согласует владелец. Перед публикацией preview владелец утверждает выбранную лицензию собственного кода, допустимость комплекта зависимостей и выпуск без подписи. Эти решения не блокируют подготовку и тестирование installer, но блокируют публикацию бинарного release. Подпись не гарантирует отсутствие всех предупреждений SmartScreen. [Inno SignedUninstaller](https://jrsoftware.org/ishelp/topic_setup_signeduninstaller.htm).

## Этапы реализации и проверяемый результат

Это последовательность работ для обсуждения; подробный план с интерфейсами и тестами составляется после ревью этого решения. Независимые исследования выполняли три агента: упаковка/runtime, выпуск/зависимости, публикационный аудит.

| Этап | Файлы/область | Результат и проверка |
|---|---|---|
| 0. Git и публикация исходников | `.gitignore`, README, master/рабочая ветка | Чистый базовый коммит, исключены credentials, локальные данные, SDK и binaries; публичный репозиторий без фиктивного EXE-релиза |
| 1. Разделение путей | новый `lib/paths.cjs`; controller, workspaces, browser, codex, render, host/loader | Разработческий и installed режимы; запуск с read-only appRoot, кириллицей/пробелами и без системного Node; существующие тесты проходят |
| 2. Миграция | новый `lib/migrate-install.cjs`; storage/auth/workspaces и настройки UI | Copy-only перенос, повторный запуск, отказ, конфликт, другая учётка UAC, недоступный старый диск; чаты и MOV не меняют пути |
| 3. Воспроизводимый payload | новые `scripts/package-release.cjs`, `scripts/verify-release.cjs`, `packaging/runtime-lock.json` | Чистая Windows-сборка из lockfile; точные runtime URLs/hashes; список файлов/версий/licenses; нет SDK, секретов и checkout-путей; рендер обоих движков из staging |
| 4. Installer/Repair | новый `packaging/windows/resolve-assistant.iss` и install transaction metadata | Fresh install, upgrade N→N+1, repair, отказ при работающем Resolve, автоматический возврат при обработанной ошибке и ручной Repair после аварийного обрыва; uninstall сохраняет данные; никакого npm на машине пользователя |
| 5. Release pipeline | новые `.github/workflows/ci.yml`, `.github/workflows/release.yml`; README и инструкция выпуска | CI запускает tests/check/render без SDK; tag запускает packaging и создаёт draft release; secrets подписи доступны только trusted release job |
| 6. Живая приёмка | чистая Windows 11 x64 + Resolve Studio, отдельный отчёт | Установка без Node/npm/Git, вход, генерация, preview, alpha MOV, Media Pool; обновление и повторный запуск сохраняют данные; затем публикация проверенного draft |

При реализации сначала тест на каждую опасную границу (пути, сохранность данных, прерванное обновление), затем минимальная реализация. Агентам давать независимые области в отдельных worktree/ветках; общие интерфейсы путей согласовать до параллельной реализации. После каждого этапа — ревью, затем итоговый PR в master. Никакие ветки не сливаются автоматически только потому, что план написан.

## GitHub Releases

Версия — из package.json; manifest, metadata и Windows VersionInfo генерируются. Перед созданием тега проверяется совпадение версии. Предлагаемый первый EXE — preview-релиз `0.2.0-preview.1`, а не переобозначение исходного `0.1.0` как готовой установки.

Публикуемый комплект: setup.exe, SHA256SUMS, THIRD-PARTY-NOTICES, release manifest/SBOM, необходимые исходники сторонних бинарников или допустимый их условиями способ предоставления, release notes с испытанными версиями Resolve/Windows и известными ограничениями. SHA256 подтверждает целостность при доверенном источнике хеша, но сам по себе не является подписью издателя.

Pipeline: checkout точного тега → закреплённые инструменты → чистые зависимости → tests/check/smoke → allowlist staging → проверка состава и лицензий → Inno → подпись при наличии → хеши → draft. SDK/Resolve-тесты выполняются на отдельной контролируемой машине; отсутствие Resolve на CI не считать успешной живой проверкой. Untrusted PR не получает signing token и права публикации.

После чистой приёмки публикуется draft с уже загруженными assets. Исходные ZIP/TAR, которые GitHub добавляет автоматически, не являются пользовательским установщиком. Один asset должен быть меньше 2 GiB; измерить размер реальной сборки. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases). Immutable releases можно включить после проверки процесса draft→publish: [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

## Критерий готовности

Человек на чистой поддержанной Windows с Resolve Studio скачивает один EXE, устанавливает и выполняет локальный render/import без среды разработки; с собственным доступом ChatGPT выполняет генерацию. Новый EXE обновляет приложение и сохраняет авторизацию (если действительна и доступна), настройки, чаты, неизменные пути MOV и ссылки Media Pool. Для первого переноса прототипа допускается согласованный сброс недоступных UI-предпочтений; для EXE→EXE он не допускается. Обработанная ошибка/отмена установки оставляет рабочую предыдущую версию; после аварийного обрыва допускается ручной Repair, восстанавливающий согласованный набор без потери данных. Uninstall сохраняет данные. Права распространения компонентов и сведения о подписи отражены в release.

Независимое ревью решения выполнено 31 октября. Уточнены граница автоматического восстановления, поведение отказа от миграции, область Repair после обновления Resolve и исключения для legacy UI-предпочтений. Решения владельца о лицензии и публичном неподписанном preview остаются отдельными условиями бинарного выпуска.

До этого момента GitHub содержит исходники прототипа и план; наличие репозитория и зелёных тестов не означает готовность массового EXE.
